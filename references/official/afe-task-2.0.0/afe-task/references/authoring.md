# 构建模式

适用于新建、迁移、修改或修复 AFE 任务包。<skill_dir> 是 afe-task 根目录；相对资源从这里定位。先读 [共建指南](../assets/task-template/共建指南.md)，不要让作者另找 Harbor 文档才能完成常规供题。

## 理解已有材料，补齐科学决定

先阅读作者提供的研究说明、代码、数据清单、评价方法和已有记录。用简短文字整理：研究缺口与拟新增贡献、Agent 可用输入、最终产物、必要约束、目标达成条件及验证方法。已给出的信息直接使用，不让作者重复填表。

只询问影响实现的缺失信息，优先合并同一轮问题：

- 什么结果才算完成，依据是什么？优化题的专家目标、映射及超目标判据；其他题的必要科学条件和如何给分。
- 谁或什么程序能验证这些条件？需要的数据/工具怎样取得，哪些材料对 Agent 隐藏？
- 产物是什么、有哪些预算或调用限制？代码/模型需有实际调用接口；服务需说明反馈和预算。

普通目录名和文件组织可自行安排。专家目标、评价阈值、科学对照和授权边界不能凭默认值补齐。对已明确的选择不重复确认。没有参考方法就省略 solution；不要求作者先解出开放问题。

若科学决定或材料未齐，仍可制作可交接的草稿：完成确定的部分，将具体缺口写入可选的补充材料/材料清单与缺失项.md，指出需作者提供什么。草稿不能保留合成目标当真实目标，不能用文件存在或无条件通过来冒充科学评分；评分尚未实现时应明确报 evaluation_error 并说明原因，而不是输出科学 0 或 100。依赖未决科学条件的实现等答复后继续。

## 选择并复制模板

在用户指定的可写输出位置创建或修改任务；没有指定时使用当前允许写入的项目目录。新建题包复制模板，不修改 skill 自身或原始数据。迁移默认保留来源，明确要求原地修改时遵循该范围。

- 普通文件、报告、证明、代码或模型交付：复制 assets/task-template/task_package/，替换合成输入、题文、评价逻辑和元信息。目录结构不限定科学产物的类型。
- 中途公开自查：按需添加 environment/tools/ 并在 Dockerfile 复制；不需要服务时不引入 Compose。
- 隐藏数据、受控查询或可信预算：可选 assets/task-template/可选示例/validation_task/，复制为 task_package/，替换合成服务逻辑；具体交接见共建指南第 7 节。
- 参考方法：按需从可选示例/参考方法/取目录结构；可只有 info.json。
- 二分类：可借鉴可选示例/二分类评分.py 的 0/100 输出，不要求人为制造部分分。

模板副本中的 example_only、题名、作者、数据、目标、时限和资源要按实际材料调整。替换不再适用的合成文件；保留尚未替换的内容时明确标成草稿缺项。模板不是经过科学验收的真实题。

## 实现与对接

按 [协议要点](afe-contract.md) 实现，内部文件组织由题目需要决定：

1. instruction.md 覆盖研究目标、输入与工具位置、约束、最终产物格式/路径和完成条件；不强制章节，不需要公开分数映射。
2. task.toml 填写运行资源和 metadata.afe；主分映射仅登记实现地址和简述，参数留在作者代码中。参考/validation 按需登记。
3. Dockerfile 明确复制输入、工具和依赖。逐一对齐“题文产物 → artifacts 收集 → tests 读取”，不可只写配置却不实际交付材料。私有评价数据保留在评分环境或服务中。
4. tests/test.sh 为固定入口。保留随包 tests/afe_contract.py，调用 write_result 或自行实现等价输出；区分无效提交、评分故障和科学未达标。作者自选映射，但不让舍入或无关加分把未达标变成 100。
5. 对机制/证明/证据题，可以用可复核判据或专家/模型辅助判断，不强造 raw 指标。公开完成条件写入题文，具体判据与依据可放 tests 的代码或说明，并能对应实际判定路径。不能把“写了一份报告”实现成“科学目标已成立”。
6. 确实需要人工复核时才使用 pending_review；与作者落实复核者、所需材料和最终结果如何回填。尚未接入就注明待接入，不声称 Harbor 会自动完成复核。

资源定位、外部获取方式和特定版本按指南说明。缺访问条件或凭据时记录配置需求，不把密钥放入题包。平台接入/ 是给运行方的工具，不是 Agent 自动调用的 harness。

## 自查、修正与交付

先运行静态结构检查，报告写在任务包外：

```sh
python3 <skill_dir>/scripts/check_structure.py <task_dir> --output <review_dir>/structure.json
```

退出码 1 是发现结构负项，仍须读报告和继续内容检查；2 是工具/输入错误。修改题包后刷新报告时，使用新的输出文件名；确需替换本轮已有的 structure.json 或 review.md，可在对应脚本命令末尾加 --overwrite，不手工修改检查结果。按 [审核流程](review.md) 阅读最终文件和已有证据，使用 [质量标准](rubric.md) 与适用的 [题型指引](task-type-checks.md)，生成 review.md；摘要标明“构建后自查”。

在构建授权范围内修正已明确的实现问题，刷新受影响的检查和报告。科学目标不明确的事项保留具体问题，不为了提高审核档位擅自改目标或标准。结构通过不等于科学合格。

允许且有必要时，用小型、明确标注的合成输入核验格式、结果状态或局部评分逻辑；记录实际执行范围。环境构建、服务启动、实际科研计算取决于运行资源与用户授权；受限的管理工作区不执行这些任务。不能将合成测试写成科研成果或实际容器联调。

交付任务目录、统一 review.md 和剩余事项；必要补充材料与 task_package/ 同级。需要提交 ZIP 时只打包 task_package/ 和必要的补充材料/，不混入整个 skill、自查报告、模板说明或平台接入工具；task_package/tests/ 属于实际评测材料须保留。依赖外部数据时按约定交付获取说明，不擅自复制大数据。提交到端砚或公开发布按用户另行授权执行。
