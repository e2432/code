# Agent Frontier Exam 共建指南

**统一提交入口：**[**书生·端砚 ReX 科学共研计划**](https://discovery-home.intern-ai.org.cn/home/event/rex/index.html)，点击“提交科学问题”。文末提供 AFE 任务包模板和自查工具。

提交信息填写注意事项：

- 等级默认填写“L1”，可视题目考虑填写“L2”，如果不确定可以填“暂不确定”
- 合作来源填写“学术合作”

AFE（Agent Frontier Exam）希望与领域研究者共建一个科学发现平台，让智能体围绕前沿科研问题反复探索、验证和改进。选题的核心是：模型一旦达成目标并经验证，就能形成此前已有研究与方法尚未实现的科学突破贡献。本轮征集 L1：限定目标的科研挑战。也即要设定清楚研究目标。即使任务本身还有在目标之上的持续推进空间。

## 1. 我们希望征集什么样的问题

一个任务围绕一个可独立验收的科研目标。出题时先说明研究缺口、预期贡献和验证方式，再按模板完善材料。

- 有明确的突破目标。说明发布时已有研究与方法尚未做到什么，达成目标将跨过哪一条科学边界，并给出相关研究、专家判断及核对日期。题目目标应对应真实的新贡献，不能仅是模型此前不会完成的已知任务。
- **需要实质研究判断。** 包含推断、证明、建模、设计、实验分析或优化。已有成果可以作为基础；侧重实质性目标，仅重复已知结论或改名包装的任务需重新选题。
- **研究范围可限定。** 说明输入、可用工具、资源预算、固定条件和允许探索的空间，明确最终产物。
- **成功可以检验。** 可以没有标准答案，但应提前说明科学必要条件及取证方式。程序、仿真、形式检查、专家或模型辅助评价均须能对应具体证据。
- **贡献主张与证据相称。** 区分预测、仿真和实验结论；预测准确不等于机制已成立。否定结果能否达标取决于预先设定的目标，不能把任何未完成都算作成功。

以下仅为出题方向和验证方式的示例，包括但不限于这些形式；欢迎其他能产生可验证科学突破贡献的题目。不同形式可以交叉，不决定 Level，也不替代科学领域分类。

| 题型 | 可以提出什么目标 | 主要怎样检验 |
|-|-|-|
| 方法与性能推进 | 在固定预算下达到新的精度、效率或可靠性目标 | 同条件测试；检查约束、泛化及误差 |
| 新对象与候选设计 | 设计符合多项要求的材料、分子或结构 | 对象合法性、必要约束与性质；注明计算或实验验证 |
| 规律、方程与模型发现 | 建立能解释新条件的关系式或规律 | 科学约束、独立验证和适用范围 |
| 机制辨析与因果解释 | 区分一个现象背后的竞争解释 | 辨别性证据、关键对照、混杂与结论边界 |
| 适用边界、失效与反证 | 明确理论何时失效，或找到有效反例 | 范围、边界两侧证据、误差排查与反例有效性 |
| 数学证明、理论与构造 | 证明限定命题、改进一个界或给出新构造 | 假设与推导、形式检查、精确计算或专家证明审查 |
| 新现象、测量与证据 | 确认新现象，或获得能回答新问题的可靠测量 | 来源、独立支持、不确定性及伪影/偏差排除 |
| 实验设计与预算内探索 | 决定下一次测什么，更快找到目标或获得信息 | 可核对的测量记录与预算；按目标验收发现或学习效果 |

例如：研究一个近似模型在哪些条件下失效，可以以边界图和证据为成果，不必一定提出更低误差的新模型；研究两种机制能否区分，可以接受充分检验后的否定结论，但“没有找到候选”不能替代“构造合格候选”的目标。

可参考文末“研究目标与评价说明.md”先写清这些问题，此文件仅供梳理题目内容，不强制提交。

征集领域包括生命、化学、材料、物理、天文、地球、能源、信息、神经科学、医学、数学，欢迎跨领域问题。

## 2. AFE 的 Level 分级

Level 描述科研定位和协作方式，不是任务包质量分数。当前版本主要征集 L1层级的题目；L2 留待后续版本，L3 本轮不征集。

| 等级 | 科研定位 |
|-|-|
| **L1** | 限定目标的科研挑战：事先明确研究问题、目标范围、条件与验收标准；达成目标应构成对已有研究边界的突破，形成此前研究与方法尚未实现的科学贡献。首版全部为 L1。 |
| **L2** | 重大科研挑战：更加侧重科学重大意义，结合潜在领域进展、研究与验证成本（如湿实验）、资源及协作需求等因素综合判断。 |
| **L3** | 开放的原创科研探索：在 L2 基础上追求具有诺奖级意义、从 0 到 1 的突破。平台不预设具体题目、研究方向或预期成果，由研究主体在探索中自主提出问题并形成方向。属于平台长期愿景。 |

L1 同样以此前未实现的科学突破贡献为目标；L2 更强调重大科学意义及研究组织与验证需求；L3 进一步开放问题和方向的形成。是否有参考解、单次费用高低或是否涉及湿实验，均不能单独决定等级。最终分级由 AFE 团队结合具体题目确认。

## 3. 下载模板，准备一个任务包

使用文末 **AFE_task_package_template_v1.0.1.zip**。它延续 ReX 的 Harbor 目录结构，加入 AFE 1.0 的元信息和评分输出约定，按 Harbor 0.25.0、Linux 独立评分环境编写。常规供题阅读本指南并修改模板即可。希望由 agent 协助构建时，推荐下载文末 afe-task-2.0.0.zip；它已包含同版指南、完整模板和自查工具，无需重复下载模板。

```text
task_package/
├── task.toml                  运行配置与 AFE 元信息
├── instruction.md             Agent 实际读取的题文
├── environment/
│   ├── Dockerfile             解题环境；复制输入、安装工具
│   ├── input/                 输入数据，按题目需要
│   └── tools/                 Agent 使用的工具，按需
├── tests/
│   ├── Dockerfile             独立评分环境
│   ├── test.sh                固定评分入口
│   └── ...                    作者的评分实现与评测材料
└── solution/                  可选；每个参考方法一个子目录
    └── method_a/

补充材料/                      按需提供材料清单、来源限制、验证记录
```

模板中的数据、目标和分数均为合成演示，请替换成真实题目。默认任务不带参考方法或额外集成目录；参考方法、二分类评分和带 validation 服务的例子在“可选示例/”中。

材料尚不完整也可提交。请如实选择“部分材料待补充”或“需协助构建任务”，在补充材料中说明缺失项及需要的协助。

## 4. 题文和配置分别写什么

### 4.1 instruction.md：让 Agent 知道怎样开展研究

章节名称和顺序可以自由安排，但需要覆盖：

| 信息 | 应说明什么 |
| --- | --- |
| 科研目标 | 研究背景、尚未解决的具体问题、达成后的新贡献与范围 |
| 输入 | 在运行环境中的位置、文件格式、字段/单位、获取条件 |
| 环境与工具 | 可用软件，工具或接口的实际位置与调用方式 |
| 约束 | 时间、算力、数据使用范围、查询或实验预算，以及候选合法性等条件 |
| 最终交付 | 文件/目录的绝对路径、格式、必要字段；代码或模型还应说明调用接口 |
| 验收标准 | 怎样判断好坏、什么条件算完成；可继续优化的题说明优化方向 |
| 中途验证 | 有则说明调用、反馈、预算；没有专用工具则简要说明 |

**输入、工具和输出的位置及格式必须与实际配置、代码一致。** 例如题文要求写入 `/work/output/predictions.csv`，配置就要收集 `/work/output`，评分程序也要读取同一文件并遵循同一格式。只有文字说明而没有实际交付，无法完成对接。

### 4.2 task.toml：告诉运行器怎样准备环境和交接结果

下面是最小示例；资源数值按题目调整。模板里的 AFE 协议版本由模板维护，作者修改题目时更新 `task.version`。

```toml
schema_version = "1.4"
artifacts = ["/work/output"]

[task]
name = "afe/your-task-name"
version = "0.1.0"
description = "一句话说明科研目标"
authors = [{ name = "作者或团队" }]

[metadata.afe]
protocol_version = "1.0"
level = "L1"
domains = ["材料"]
supports_over_target = true

[metadata.afe.score_mapping]
url = "tests/score.py"
description = "描述如何由本题评价结果得到主分；具体参数由作者代码维护。"

[agent]
timeout_sec = 3600

[environment]
workdir = "/work"
cpus = 2
memory_mb = 4096
storage_mb = 10240
gpus = 0
build_timeout_sec = 600
network_mode = "no-network"

[verifier]
environment_mode = "separate"
timeout_sec = 300

[verifier.environment]
workdir = "/tests"
cpus = 1
memory_mb = 2048
storage_mb = 4096
gpus = 0
build_timeout_sec = 600
network_mode = "no-network"
```

| 配置 | 含义 |
| --- | --- |
| `task` | 题名、版本、简述、署名；题名使用 `afe/英文短名称` |
| `metadata.afe.domains` | 从生命、化学、材料、物理、天文、地球、能源、信息、神经科学、医学、数学中选择，可多选 |
| `supports_over_target` | 是否定义了超过满分目标的判据；不支持时填 false |
| `score_mapping.url` / `description` | 分数映射实现的位置和简述； |
| `agent.timeout_sec` | Agent 解题时限，单位秒 |
| `environment` | 解题环境资源；内存/存储单位 MB，workdir 是容器内默认工作目录，build_timeout_sec 是构建时限 |
| `verifier` 及其 `environment` | 评分时限、独立评分环境及资源；模板明确填写评分资源 |
| `artifacts` | 结束后收集并交给独立评分环境的文件/目录；评分时恢复到同一绝对路径 |

`environment/` 是构建材料，不会自动完整交给 Agent。以模板为例，Dockerfile 中 `COPY input/ /work/input/` 才将输入放到 `/work/input/`。工具同理。`tests/` 进入独立评分环境，参考资料不默认交给解题 Agent。

需要联网时将 `network_mode` 改为 `public`，或使用 `allowlist` 并填写 `allowed_hosts`，与实际依赖一致。已有镜像可用 `docker_image` 指定；运行器必须支持所选配置。外部服务说明凭据配置方式即可，不上传密钥。数据无法打包时说明获取方法和访问条件。

AFE 的 `url` 字段允许包内相对路径或 HTTPS 地址：相对路径以任务根目录为起点。地址只负责定位，运行所需材料仍须实际交付到相应环境；正式评测使用固定版本。

## 5. tests：固定入口和输出，内部实现由作者决定

AFE任务包的分数分为两部分。一部分是不做统一要求的原始指标。另一部分是要求需映射到[0,100]分的统一指标。

Harbor 调用 `tests/test.sh`。它可以调用任意适合本题的程序、仿真或评价工具，不要求内部固定拆成几个文件。最终在评分容器中写出：

```text
/logs/verifier/afe_result.json    AFE 科学结果
/logs/verifier/reward.json        Harbor 数值结果，有最终成绩时提供
```

正常结果示例，数字均为假设：

```json
{
  "status": "evaluated",
  "score": 75,
  "raw": {"prediction_error": 9.5},
  "target_exceeded": false
}
```

`status` 和 `score` 必须出现。`raw`、`target_exceeded`、`notes` 可选；没有时省略。raw 是对象，里面的指标和嵌套结构由题目决定，不要求所有科研题都有数值原始指标。notes 是简短补充文字，不要求评分程序生成总结。

**score 为有限的 0–100 数值。100 表示全部必要科学条件和预设目标均成立；优化题的满分目标由专家论证。** 映射由作者实现，不能仅靠舍入让未达标结果成为 100。二分类题可只输出 0 或 100。即使继续优化超过目标，主分仍封顶 100。

`target_exceeded=true` 表示本次确实超过预设目标，要求题目声明支持，且 score=100。省略表示未报告这个判断，不等同于 false。它可用于显示“100+”，不自动改变 Level。

### 状态和对应字段

| status | 含义 | score | 其他字段 |
| --- | --- | --- | --- |
| evaluated | 已完成可信评价，目标可能达成，也可能未达成 | 0–100 | raw、target_exceeded 可选；不使用 error |
| invalid_submission | 不符合事先写明的交付要求，如缺文件或格式错误 | 0 | 必须有 error；省略 raw、target_exceeded |
| evaluation_error | 评分程序、依赖或必要服务出错 | null | 必须有 error；省略 raw、target_exceeded |
| pending_review | 事先约定的必要人工复核尚未完成 | null | 可选预留；省略 error、raw、target_exceeded |

所有状态均可带可选 notes。pending_review 不需要普通自动评分题实现；确实需要人工验收时，与团队明确复核者和补入最终成绩的流程。它不是题包的入库审核状态。

```json
{
  "status": "invalid_submission",
  "score": 0,
  "error": {"code": "missing_output", "message": "缺少 /work/output/predictions.csv"}
}
```

error 只要求 code 和 message：前者是作者定义的错误类别，后者是具体诊断。同样语义使用上述状态名称和结构；作者可以提出新状态，在随包说明中写清语义、字段和是否已有最终成绩，由平台接入。未知状态会保留并提示对接，不自动记为零分。

### Harbor reward 与主分的关系

本项目用目标达成率作为主榜口径：evaluated 且 score=100 时写 `{"reward":1}`；其他已评价结果及 invalid_submission 写 `{"reward":0}`。科研主分仍完整保存在 afe_result.json。

pending_review、evaluation_error 和尚未接入的扩展状态没有最终 reward，不填假的零分。原生 Harbor 会记录缺少 reward 的情况；平台应读取 AFE 结果区分原因。模板附“平台接入/”收集工具处理这些结果，不要求作者另做一套平台逻辑。

模板提供 `tests/afe_contract.py` 帮助检查和输出两份文件，作者可直接调用，也可自行实现相同接口：

```python
from afe_contract import write_result
write_result(
    {"status": "evaluated", "score": 75, "raw": {"mae": 9.5}},
    supports_over_target=True
)
```

评分应真正核验核心科学条件，不能用格式或报告分补足未成立的科学结论。参考成绩可选，但证明本题主张所必需的对照与材料仍需落实；评价实现、日志和任务产物共同支撑判断。

## 6. 可选参考方法：一个目录，一份 info.json

参考方法、代码和参考成绩都可选；没有达成目标的方法也可以提交题目。作为正式 reference 提供时，请选择相关问题和条件下的现有最佳方法，准确描述原理和适用条件。

在 `solution/method_a/info.json` 填写：

```json
{
  "name": "方法 A",
  "proposed_at": "2025-03",
  "description": "说明方法原理及适用条件。",
  "source_urls": ["https://example.org/method-a"],
  "notes": "仅提供方法资料，尚未在本题条件下测量。"
}
```

必填 name、proposed_at、description、source_urls；方法提出时间按已知精度填写，来源可以是论文、代码或随包资料。可选 raw、score、notes。raw 是对象，score 是本题条件下的 0–100 分；未测时省略，也可明确填 null，不填 0 冒充已测。文献成绩与本题不具可比性时，在 notes 说明。

一个目录可以只有 info.json；可运行代码或说明原理的文件均按需提供。默认不要求 solution/solve.sh；需要自动运行某个参考方法时再对接运行入口。

在 `metadata.afe` 段增加可选地址列表，支持多个方法：

```toml
reference_urls = ["solution/method_a/", "solution/method_b/info.json"]
```

每个地址定位方法目录或 info.json。方法描述只写在各自 info 中，不在 task.toml 重复填写。

## 7. 按需提供中途验证和外部服务

只做公开格式自查时，可将脚本放入 `environment/tools/`，在 Dockerfile 复制到 `/work/tools/`，再在题文说明调用方法。

需要隐藏数据、受控查询或可信预算记录时，Agent 环境放客户端，计算和记录放在独立服务。模板的 `可选示例/validation_task/` 展示了完整文件组织：

```text
environment/
├── Dockerfile
├── tools/validate.py
├── docker-compose.yaml
└── validation_service/
    ├── Dockerfile
    ├── server.py
    ├── export_state.py
    └── ...
```

`docker-compose.yaml` 定义并启动 main 和 validation 两个服务；`build.context: ./validation_service` 指定服务构建目录。Agent 通过客户端访问 `http://validation:8000`。这类示例使用支持 Compose 的运行后端，服务资源另行配置。

题文说明请求/响应、反馈范围、预算和失败请求的计费方式。task.toml 可登记客户端：

```toml
[metadata.afe.validation]
command = "python3 /work/tools/validate.py --candidate-id <候选ID>"
description = "查询候选结果；反馈和预算规则见题文。"
```

如最终评分需要服务记录，将下面的产物声明合并到 task.toml 顶层，并配置收集命令：

```toml
artifacts = [
  "/work/output",
  { source = "/validation_snapshot/session.json", service = "validation" }
]

[[verifier.collect]]
service = "validation"
command = "python3 /service/export_state.py"
timeout_sec = 30
```

运行器启动服务，Agent 调用客户端；解题结束后，运行器调用 export_state.py 封存服务记录，再交给独立评分环境执行 test.sh。评分器读取服务导出的记录，不使用 Agent 自报的查询历史。模板例子已提供这些脚本，真实服务的算法由作者替换。

只有需要额外平台适配时才提供根目录 `harness/`，例如外部实验平台的会话创建、记录导出、资源清理脚本和调用说明。这些由平台明确接入，不会因放入目录自动执行，也不是让被测 Agent 管理评测服务。普通题和上述 Compose 示例均不需要 harness。

## 8. 使用 agent 构建与审核

下载并解压 **afe-task-2.0.0.zip**，保留完整 afe-task/ 文件夹。它包含本指南、任务模板、构建流程和审核工具；不熟悉 AFE 或 Harbor 的共建者也可以从已有科研材料开始，由 agent 引导完善。

**构建或修改任务包：**

```text
请阅读 /path/to/afe-task/SKILL.md，使用构建模式，
根据我提供的科研问题和材料，在 /path/to/output 中制作 AFE 任务包并自查。
科学目标、满分条件或必要材料不明确的地方请向我确认。
```

agent 会整理研究目标与验收条件、选择模板、生成或修改文件，再进行自查。关键科学目标和专家满分条件由作者确定；材料不完整时可先形成注明缺口的草稿。参考解保持可选，不需要先解决题目。

**只审核已有任务包：**

```text
请阅读 /path/to/afe-task/SKILL.md，使用审核模式，
静态审核 /path/to/task_package 及我提供的补充材料，
报告写到 /path/to/review_output，保持任务包只读。
```

审核从科学价值、任务定义、数据环境、评价有效性与健壮性、隔离、验证证据、来源等八项检查，产出统一 review.md，每项为 0–3 档或“待核实”，不合成质量总分。审核模式不会直接修改题包；构建后的报告标明自查，不冒充独立审核。新版已包含原 afe-harbor-review 的审核功能，无需另装旧版。

也可以直接运行脚本。在独立模板解压目录执行下面命令；使用 skill 内附模板时，先进入 afe-task/assets/task-template/，将 task_package 替换为实际任务目录：

```sh
python3 自查工具/check_structure.py task_package --output structure.json
python3 自查工具/afe_contract.py result /path/to/afe_result.json --supports-over-target true
```

第二条命令仅在已有评分结果时使用，true/false 与题目声明一致。Python 3.11+ 可直接运行；Python 3.8–3.10 需有 tomli。结构脚本不运行任务或构建镜像：退出码 1 表示发现结构问题，2 表示工具或输入错误；仍需阅读报告中的待核实项。Schema 已随包提供，无需另填同内容 JSON。

自查用于发现缺口，不是初次提交的门槛。构建默认静态自查，审核只读材料和已有证据。运行验证按授权和可用环境开展，并区分合成样例检查、实际运行和未验证事项；不会自动开展科研实验、提交端砚或公开发布。

## 9. 怎样提交

1. **填写端砚表单。** 说明提交团队、科学问题、建议等级、已有基础、Agent 输入、预期产物、资源、成功标准和材料完备程度；可在说明中注明“AFE 共建”。
2. **上传一个任务的 ZIP。** 将 task_package/ 和必要的补充材料/ 放在 ZIP 根目录。无需包含 afe-task/ 工具目录、自查报告、“共建指南.md”“可选示例/”“自查工具/”“平台接入/”和模板清单；task_package/tests/ 是实际评测材料，应保留。使用 validation 示例时，将选中的任务目录重命名为 task_package/ 后提交。上传大小和修订方式以提交时页面规则为准。
3. **确认材料使用范围。** 在网页分别确认任务使用、训练／能力改进、公开发布的选择，披露实际限制。提交不等于自动同意训练或公开；AFE 公开发布前会另行核对适用范围。
4. **检查后提交并保留副本。** 后续补充或修订请与对接团队确认，注明任务名称和版本关系。

团队、授权等网页信息不必在包内重复填写；运行必需的配置仍需提供，文件级来源和特殊限制按需补充。提交后，团队结合科学价值、分级、材料、评价与资源反馈对接事项。
